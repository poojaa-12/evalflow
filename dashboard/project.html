Run Project

What Evalflow is

A synthetic incremental eval runner. It is not a Nuro system and not a real autonomy stack. The evaluator is a deterministic stand-in, so a cache hit can be checked exactly.

What it is doing

Each scenario depends on a subset of model components: perception, planner, prediction, or a pair of those. The runner evaluates the suite, writes a JSONL run file, and can compare two runs.

The cache key is a sha256 of three things: the evaluator version, a fingerprint of the scenario, and hashes of only the components in depends_on. A planner edit therefore recomputes planner-dependent scenarios and leaves the rest as cache hits.

On the measured suite that is 70 misses and 130 hits out of 200. Perception-only and prediction-only metrics stay identical. Six unprotected-left cases flip from pass to fail. The run page is that result, row by row.

v1 and v2 share perception and prediction parameters. v2 changes only planner.conservatism, from 0.8 to 0.35. The suite is 120 perception, 40 planner, 20 perception+planner, 10 prediction, and 10 planner+prediction. That mix is why a planner-only edit invalidates 70 scenarios and no others.

How

  • Canonical JSON (sort_keys, compact separators) is hashed before it enters the key. Component order in depends_on is normalized, so the fingerprint does not depend on file order.
  • The evaluator receives only the depends_on parameters. An extra component is rejected. An unrelated edit cannot change metrics without changing the key.
  • Cache writes use a temp file in the destination directory and os.replace. A missing entry is a miss. An unreadable or schema-invalid entry logs a warning, is recomputed, and is overwritten. The rest of the run continues.
  • Hits record duration_s of 0. Misses go through ProcessPoolExecutor. The worker is a module-level function so it pickles. One worker exception becomes a row with error set. Other scenarios still finish.
  • Compare joins on scenario id. Pass true to false is a regression. Distance worsens below a 0.05 m tolerance. Jerk worsens above a 0.10 tolerance. Improving one metric and regressing another still counts as a regression.
  • Simulated cost is time.sleep. The default is 0.1 s so the sleep dominates process-pool startup. Tests pass cost_s=0. Bumping synthetic-v1 invalidates every key.

Why

A full eval is the expensive object. Most model edits do not touch every scenario. If the cache key includes the whole model, one planner change throws away perception-only work. If the key ignores dependencies, a real change is a silent hit.

The rule has to be visible. The key lists the components that were hashed. The run header lists hits, misses, and wall clock. Compare names the pass flips before the metric-only regressions. An engineer can point at a row and say why it moved.

Why this is the fit for Nuro

Nuro’s eval problem is not drawing a chart. It is knowing which scenarios a component edit invalidates, recomputing only those, and handing an engineer a result they can defend. Pooja built this prototype around that rule.

The cache key includes the evaluator version, the scenario, and only depends_on. The worker never sees the other components, so an unrelated edit cannot change outputs without changing the key. A corrupt cache entry is a miss, not a crash. One failed scenario does not drop the rest of the run. The comparison treats a mixed improve-and-regress row as a regression, and it sorts pass flips first.

The stack is synthetic on purpose. Calling it a Nuro system would hide whether the invalidation is actually correct. Here the proof is checkable: 70 keys change, 130 metrics match bitwise, six unprotected-left passes flip to fail, and the speedup is 2.3971 on the recorded bench.

That is the piece of eval infrastructure worth showing. Contracts, partial invalidation, and a page someone else can read. Ray, Parquet, bootstrap confidence intervals, and watch mode are out of scope for this prototype.
